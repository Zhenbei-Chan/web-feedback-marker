# Issue #7：AI 页面检查实现方案

## 背景

用户希望插件不仅支持人工网页批注，也能一键检查页面中的基础内容问题，例如错别字、表达不清、占位文案、上下文不一致等。检查结果需要直接标在页面上，并能进入最终报告。

这个功能必须能公开给其他人使用，所以不能依赖作者自己的 API Key，也不能默认上传用户网页内容。

## 结论

推荐方案：

> OpenAI-compatible BYOK 架构 + 智谱 / DeepSeek 预设 + AI 待确认标记流程。

第一版不做“自动改文案”，只做“AI 检查并生成待确认标记”。

## 核心原则

- 默认不开启 AI。
- 用户主动点击后才检查。
- 用户自己配置 API Key。
- API Key 只保存在 `chrome.storage.local`。
- 不上传截图。
- 默认不上传 URL。
- 只发送抽取后的页面文本块。
- AI 结果默认是“待确认”，不能直接等同于人工确认。
- 用户确认“非问题”时删除该 AI 标记。

## Provider 选择

### 智谱 AI

适合第一版作为中文轻量检查预设。中文理解能力较好，适合错别字、语病、占位符和表达问题。

文档中不要承诺“永久免费”，只说明用户可自行选择其可用的免费或低成本模型。

### DeepSeek

适合作为 OpenAI-compatible 预设。逻辑理解能力更强，适合检查上下文矛盾、前后表述不一致等问题。

### OpenAI-compatible 自定义服务

必须支持。很多用户可能会使用公司内部模型网关、OpenRouter、私有化网关或其他兼容接口。

### 百度千帆

可作为第二阶段。它的鉴权流程相对复杂，不适合作为第一版默认实现。

## 第一版能力

1. Popup 和页面悬浮菜单新增“AI 检查页面”。
2. 未配置服务时，引导用户配置 Provider、Base URL、Model、API Key。
3. 抽取当前页面可见正文文本。
4. 分块调用 AI 服务。
5. 将返回结果映射回页面文本位置。
6. 页面内显示 AI 待确认标记。
7. 用户可将 AI 结果加入正式反馈，或标记为非问题。
8. 非问题直接删除；加入反馈后从 AI 待确认列表移除。
9. PDF 导出时，人工反馈优先，剩余 AI 待确认结果放在最后。

## PDF 展示规则

PDF 顺序：

1. 人工反馈。
2. AI 检查结果。

AI 检查结果区域需要显示：

- 状态：待确认。已确认的 AI 结果已转为人工反馈。
- 分类。
- 原文。
- 建议。
- 原因。
- 日期。

被删除的非问题不展示。

## 按钮命名

推荐：`AI 检查页面`

原因：

- 用户能直接理解是在检查当前网页。
- 不局限于“错别字”。
- 比“扫描低错”更专业，也更适合作为公开开源插件。

## 风险

- AI 误报不可避免，所以必须保留“待确认”。
- 复杂网页的 DOM 定位可能失败，需要允许“清单中有结果，但页面无精确标记”。
- API 权限不能默认放大，否则会违背插件原有低权限约束。
- API Key 本地保存不是加密保险箱，README 需要明确说明。
